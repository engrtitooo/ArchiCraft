# ArchiCraft credential remediation

The deployment log previously committed as `ERROR` disclosed four credentials. The repository repair removes that file and generated bytecode, moves all Gemini calls behind authenticated backend requests, removes signing defaults and OTP logging, and rejects the disclosed values by SHA-256 fingerprint. No disclosed credential value is retained in the repair.

## Required provider actions

Repository changes cannot revoke a Google credential or change a running Cloud Run revision by themselves. Complete the following in the owning Google accounts:

1. Revoke the exposed Gemini/Google API key in Google AI Studio or Google Cloud credentials. Review API usage, billing and audit activity since the July exposure. Create a replacement restricted to the required API and keep it in the backend secret manager/runtime only.
2. Revoke the exposed Gmail app password in Google Account → Security → App Passwords. Review account activity. Create a replacement for the configured sender if SMTP remains in use, or configure a fresh Resend credential. Never share replacement values in chat, screenshots or commits.
3. Replace `APP_PASSWORD` with a fresh password of at least 12 characters. Replace `JWT_SECRET` with at least 32 characters of cryptographically random material. Update every environment that reused these values. The new session cookie is `archicraft_session_v4`; older cookies no longer authenticate.
4. Update Cloud Run's backend secret references/environment settings: `GEMINI_API_KEY` (or legacy `API_KEY`), `APP_PASSWORD`, `JWT_SECRET`, `ADMIN_EMAIL`, and fresh SMTP or Resend settings. Remove old browser/build-time key injection. Never print a deployment environment dump into the repository.
5. Deploy the repaired revision and route traffic to it. Confirm a normal password → delivered email OTP → login → all four Gemini operations. Confirm no provider key appears in downloaded JavaScript, anonymous generation returns 401, and the old signing key is no longer accepted. Remove traffic/access to superseded insecure revisions as appropriate.

If the old exposed values remain configured, authentication, email delivery or generation intentionally returns a safe unavailable response. This is required containment; configuring fresh credentials restores normal use. A backend image import/build remains possible without runtime secrets.

## Repository history and open pull requests

The previous commits and the existing Dependabot branch can still contain the deleted log. Credential revocation is the first containment step. A normal commit cannot erase historical copies; history rewriting needs a separate coordinated change and cannot remove other people's clones. Do not treat deleting a file, closing a pull request or making a repository private as credential revocation.

Do not merge an old branch if it would restore the deleted log, bytecode or browser key injection. Review/rebase dependency changes against the repaired main branch. Run `python scripts/check_secrets.py` before commits. Keep `.env`, deployment dumps and generated bytecode out of source and image build contexts.

## Verification scope

The automated tests use synthetic credentials and mocked provider/email responses. They verify the authentication boundary, all four client contracts, SDK-to-REST payload translation, supported PNG/JPEG/WebP images, failure handling, resource limits and credential checks. Provider revocation, real delivery, billing review and production deployment must be verified in the owning accounts; local tests do not establish that these external steps have occurred.
